# TINVO Architecture

TINVO is a terminal digital audio workstation written in Rust with **no third-party crates**: only `std`, its own DSP, and direct FFI to the operating system's audio and console APIs.

Author: 𝓐.𝓒.𝓑

## Design principles

1. **The audio thread is sacred.** After the engine is built, `Engine::process` never allocates, locks, blocks or does I/O. Every buffer, voice and track slot is sized when the engine is created.
2. **One source of truth, one way to change it.** Every change to the document is an `Edit` value. The UI applies it to the `Project`, gets back the edit *as actually applied* (with values clamped), and sends that same value to the engine. The model and the engine can't drift apart, because they run the same operations, and a test proves the edits rebuild the project.
3. **Offline equals real time.** WAV export drives the exact `Engine` used for playback, so an export matches playback down to the bit (the tests check that rendering is deterministic and independent of buffer size). Exports stream to a temporary file a block at a time, so memory use does not grow with their length; the header sizes are patched at the end and the file is renamed into place.
4. **Correct before clever.** Floating-point state is flushed explicitly instead of switching the CPU to flush-to-zero mode, because changing the floating-point environment behind the compiler is unsound in Rust. Timing comes from a fixed origin rather than being accumulated, so it does not drift.

## Layers

Each layer depends only on the ones below it.


## Threads and data flow

```
 ┌──────────── UI thread ────────────┐          ┌──────── audio thread ────────┐
 │ keys → App → Project::apply(edit) │  edits,  │ Engine::process(buffer)      │
 │                 │ applied edit    │ play/stop│   drain commands             │
 │                 └──► EngineLink ──┼──SPSC───►│   fire due note-offs/steps   │
 │                                   │  queue   │   render instruments         │
 │  meters, playhead, CPU load ◄─────┼─atomics──│   mix (gain/pan smoothing)   │
 └───────────────────────────────────┘          └──────────────┬───────────────┘
                                                               ▼
                                               backend converts f32 stereo to the
                                               device format (F32/I16/I24/I32)
```

- **Recording**: the backend's capture thread converts the device format to `f32`, keeps the first one or two channels and pushes whole frames (`[f32; 2]`) into an SPSC ring of 2^20 frames; it never blocks, allocates or writes to disk. A full ring drops whole frames and counts them, so channels never swap. The UI thread drains the ring every frame into a `wav::FileWriter` (32-bit float, written to a temporary file and renamed when the take ends). Stopping joins the capture thread before the last drain, so every captured frame reaches the file. The take then loads like any other sample. The recording keeps the index of its sampler track up to date as tracks are inserted or removed, through the same path every edit takes.
- **Live notes**: the MIDI backend calls a handler on its own thread (WinMM's callback thread, a TINVO thread polling the ALSA sequencer or rawmidi, CoreMIDI's receive thread). The handler pushes each note into two `rt::Mailbox`es: one the audio engine drains at the start of every callback (up to 256 notes), one the UI drains every frame for step entry. A mailbox is an SPSC ring with a try-lock on each end, so a push or pop never waits: it fails at once if the other thread of the same side holds the lock. That makes it safe while a closed input's thread and a new one overlap, or an old engine and its replacement do. The mailboxes live for the whole session and pass from engine to engine when the audio device changes; notes queued while no engine listened are discarded. The engine plays live notes on the track named by `Command::SetLiveTrack`, which travels in the command queue, so it stays ordered with the edits. Each held note remembers its track, so its release reaches the right voice after the selection moves. Track additions and removals release every live note before indices shift.
- **Command queue** (`rt::spsc`): bounded, wait-free, cache-padded. If it is ever full, `EngineLink` keeps the remaining commands in order and retries every UI frame, so no edit is lost. The audio callback spends a fixed work budget on commands per call (track additions and removals, which move whole track slots, count 512 simple edits), so a UI that keeps sending cannot stretch a callback; the rest wait, in order, for the next call.
- **Telemetry** (`engine::Shared`): playhead step, per-track and master peaks (lock-free `fetch_max` on the bit patterns of non-negative floats), and smoothed callback load.
- **Sample buffers**: the UI loads a WAV file into an `Arc<Sample>` and sends it in a `SetSample` command. When the engine lets go of a buffer (replaced, track removed), it pushes the `Arc` into a second SPSC queue back to the UI, which drops it there, so the audio thread never frees memory. The UI counts the samples it has handed to the engine (including those the engine was created with) and not yet received back, and holds a `SetSample` command in its backlog while that count equals the queue's capacity. Every buffer the engine holds or releases arrived in such a command and is released once, so the engine's push into the return queue cannot fail. The UI keeps loaded samples by path, so undo can restore one without reading the disk, and frees a sample once no track uses it and no undo or redo step refers to it.
- **Start-up**: the backend opens the device first, then calls a factory on the audio thread with the real sample rate. That is when the engine is allocated, before the stream starts.

## Engine

- **Tracks**: up to 16 slots, each with an `Instrument`, a 64-step pattern, fader/pan/mute/solo, and smoothed left/right gains (5 ms time constant, so changes never click).
- **Transport**: 16th-note steps. The frame of step *n* is `origin + round((n + swing(n) − origin_step) × samples_per_step)`, where `swing(n)` is `percent/50 − 1` for odd *n* and 0 otherwise. A tempo change moves the origin to the current position, so the playhead stays continuous.
- **Steps and hits**: a step is a note or a chord of up to 4 notes (stored as intervals above the lowest note) with velocity, length, chance, ratchet and a micro-timing offset. When the transport reaches step *n* it queues hits, never plays them directly: step *n*'s on-time and late hits, and step *n+1*'s early ones. An early hit is at most half a straight step early, and the shortest swung step is half a straight step, so an early hit is never due before it is queued. Every queued hit fires through the same path, after note-offs and the choke check, at its exact frame.
- **Patterns and song**: each track slot holds the steps of all 16 patterns, each pattern has a length, and the song is a fixed array of pattern numbers. Each track also holds a part per song entry: follow the entry's pattern, play its own pattern (from the entry's first step, wrapping when shorter and cut off with the entry when longer), or rest; `part_position` maps the playing position to the pattern and step a track plays, and the hits, the automation segments and the UI's play column all go through it. Song entry edits move every track's parts with the entries. The engine keeps the position of the next step to play (song entry, pattern, step) and advances it one step at a time: to the next step, at the end of a pattern to the cued pattern or the next song entry, and at the end of the loop region back to its start. Because early hits of a step are queued while the previous step plays, the next position is fixed when the previous step starts; a cue or song edit made after that applies from the step after. A position made invalid by an edit (shorter pattern or song) is corrected before it is played. The playhead (entry, pattern, step) is published as one packed `u32`, so the UI never reads half of an update.
- **Automation**: each track has 4 lane slots. A lane's target is an index into the track's parameter panel (volume, pan, then the instrument's parameters), and its points are stored per pattern and step (NaN means no point, so the audio thread needs no `Option`). When a step fires, hold lanes write their point's value before the step's hits are queued. For ramp lanes the engine keeps one segment (start frame and value, end frame and value) from the current point to the next point in the pattern; ramps interpolate in the parameter's unit space (`ParamSpec::to_unit`), so log-scaled parameters glide geometrically, and both ends carry the exact point values. Ramps are evaluated on a 32-frame tick aligned to the absolute engine clock, and the render loop splits blocks at tick boundaries, so the result does not depend on the buffer size. The knob value is kept as the base: it is used before the first point of a pattern and restored on stop, and `SetParam` on an automated parameter only changes the base.
- **Channel strip** (`strip`): each track's mono signal runs through high-pass, low shelf, mid bell, high shelf, compressor and drive before the fader and pan. Its parameters follow the instrument's in one index space (`strip::track_param`), so the panel, the project file and automation lanes treat them alike. A parameter change sets a target; every 32 frames the strip moves each value about 1/30 of the way there in the parameter's own scale (a 20 ms time constant) and snaps once it is within 10⁻⁴ of the range, recomputing filter coefficients only while something moves. The countdown to the next update is strip state, so splitting a buffer differently gives the same output. A stage runs only while it changes the signal (a band is switched out once it is flat and its filter state is zero, the compressor once it is neutral and fully released), so a neutral strip is a bit-exact bypass. The high-pass and the drive are not transparent even at their lowest settings, so they crossfade in and out over 10 ms instead of switching. An opened project snaps every strip to its settings, so a render and live playback agree from the first frame.
- **Buses and master** (`mix`): after the strip, each track's signal is faded and panned into the mix; its sends tap that stereo signal (post-fader) into a delay bus, a reverb bus and a chorus bus, with send levels as further track parameters after the strip's. A fourth send feeds the key bus from the instrument's output, before strip and fader; every instrument renders before any strip runs, so the key bus is complete when a compressor switched to it reads it. The bus returns are added to the mix, the master fader follows, and the true-peak limiter runs last. A bus is processed only while something is sent to it or its tail is still above −180 dB; with no sends and the limiter off the signal path is exactly what it was without buses. The limiter adds its look-ahead (about 1.6 ms) to playback latency; offline renders run that far ahead and drop it, so exports start on the first beat. Bus and master settings are global: `Edit::SetMixParam`, saved as `mix` lines. A lane on any one track can automate one of them (lane targets from `MIX_TARGET`); the automated value overrides the setting until the lane lets go, its track is removed or playback stops.
- **Meters**: once a block the engine takes each compressor's and the limiter's gain reduction and feeds the output to a live BS.1770 meter (fixed memory: a ring of 100 ms sub-blocks and a histogram of 400 ms block loudness); the UI reads them through `Shared` with the peaks.
- **Chance**: rolled per step when its hits are queued, from a seeded generator that restarts on Play, so playback and export always produce the same sequence of hits from the start. Ratchets split the (swung) step span evenly, starting at the shifted position.
- **Removal**: a removed track's slot is swapped with an idle one of 16 fading slots, which the engine renders like a track (instrument, strip, fader, sends; no new hits) under a linear 10 ms fade, then releases its sample. The swap moves the slot's contents without allocating, and with no fade running the render skips the slots.
- **Choke**: when a closed hat fires, open hats on all tracks fade out over 12 ms.
- **Sample-accurate events**: each 64-frame block is split at every step boundary and note-off inside it. Note-offs fire before note-ons that land on the same frame.
- **Voice identity**: `note_on` returns a `VoiceId`, and note-offs target that exact voice, so retriggering a pitch never cuts off the wrong note.
- **Pan law**: constant power, −3 dB at centre. The bottom of the fader range (−60 dB) means silence.

## DSP

| Block | Method |
|---|---|
| Oscillators | Saw and square with PolyBLEP, triangle with PolyBLAMP, sine; phase kept in f64 |
| Filter | TPT/ZDF state-variable filter (LP, unity-peak BP, HP); stable under per-sample modulation |
| Envelopes | Linear attack, exponential decay/release (times are to −60 dB); retriggers start from the current level |
| Synth modulation | One free-running LFO per synth, computed per 64-sample chunk, to pitch, pulse width, cutoff and level; glide is exponential in pitch (99 % of the interval in the glide time); pitch is recomputed per sample only while gliding or under LFO pitch modulation |
| Unison | Up to 4 copies of each oscillator spread evenly across ±detune, started at random phases and summed at 1/√n so the level stays steady |
| Sampler | Samples are limited to ±1024 (+60 dBFS) when loaded, with non-finite values silenced, so the gains after them cannot overflow `f32`. 8-tap windowed-sinc (Blackman window, 256 phases with linear blending between them) or linear interpolation, over a buffer padded with zeros so reads need no bounds checks; pitch ratio 2^(semitones/12) × file rate / engine rate; loops wrap exactly; a 64-frame fade at the region end; ADSR and an optional low-pass filter per voice |
| Drums | Kick (pitch-swept sine plus click), snare (two tones plus filtered noise), hats (six band-limited squares, metallic), clap (three bursts plus tail); retriggers cross-fade the old tail over 1 ms, and parameter changes reach a hit still ringing |
| EQ | RBJ cookbook biquads (high-pass, shelves with slope 1, bell), transposed direct form II, coefficients and state in `f64`, state flushed to zero below 10⁻³⁰ |
| Compressor | Feed-forward, peak detector, log-domain gain computer with a 6 dB soft knee, smooth-branching attack/release on the gain reduction (Giannoulis, Massberg and Reiss); no work below the knee once released |
| Drive | 2× oversampling with polyphase IIR half-band filters (8 allpass coefficients, transition 0.04, 99 dB stopband, designed as in HIIR), and at the doubled rate `tanh` with first-order antiderivative antialiasing (`F = ln cosh`, evaluated overflow-free in `f64`); about 3.3 frames of delay at low frequencies, −1.1 dB at 15 kHz |
| Chorus | Interleaved stereo ring buffer; per side two taps swept in opposite directions by a rotating-phasor sine (right a quarter cycle behind left) around 12 ms, up to ±8 ms, read with 4-point Hermite interpolation; depth glides |
| Delay | Interleaved stereo ring buffer sized for two beats at 20 BPM; time glides (in `f64`, so it cannot stall) with a 50 ms time constant and reads linearly interpolated, exact once settled on a whole frame; RBJ low-pass in the feedback path |
| Reverb | Feedback delay network: 8 lines (31–74 ms, rounded to primes), orthonormal Hadamard feedback matrix, per-line gain for the decay time and one-pole damping, 4 Schroeder allpass diffusers, pre-delay up to 250 ms (gliding like the delay time); even lines feed the left output and odd lines the right |
| Limiter | True peak by 4× interpolation (12-tap Blackman-windowed sinc per phase); required gain with instant attack and exponential release, held by a running minimum over the look-ahead and smoothed by a moving average of the same length, so each delayed sample is scaled by at most its own required gain |
| Loudness | ITU-R BS.1770-4: K-weighting derived for any rate from the analogue prototypes (matching the 48 kHz table), 400 ms blocks at 100 ms hops, absolute gate −70 LUFS, relative gate −10 LU |
| Export | TPDF dither (±1 LSB) for 16/24-bit; clipped samples are counted and reported |

The editor's run loop owns the stream. It opens the configured device, falling back to the default while that device is missing. A stream that reports an error is dropped and retried with backoff (1 s up to 8 s). Every 2 s a working stream checks whether the system default changed (WASAPI reports its id) or the missing device returned, and reopens if so. Each reopen builds a fresh engine from the project and the loaded samples on the new device's sample rate, exactly as at start-up, and hands its link to the app. The audio thread is never involved: the old stream is stopped and joined before the new one opens.

## Project file (`.tvo`)

Line-based UTF-8 text with a version header (`tinvo 11`). Format 2 added `swing` and per-step chance and ratchet; format 3 adds the micro-timing offset and the chord (`-` or intervals such as `3,7,10`); format 4 adds a `sample` line to sampler tracks, relative with `/` separators when the file is inside the project folder; format 5 adds patterns (a `pattern B` line inside a track starts that pattern's steps; `pattern_length B 32` for lengths other than 16), `song A A B` and `loop <start> <end>`. Files of formats 1–4 load into pattern A. Format 6 adds automation: `lane <k> <parameter id> hold|ramp` and `point <k> <step> <value>` lines inside a track, with points belonging to the pattern of the preceding `pattern` line. Format 7 adds the channel strip's parameters as ordinary `param` lines; only values away from the strip's neutral defaults are written. Format 8 adds the sends (`param send_delay -12`) and the bus and master settings (`mix reverb_decay 2.4`), again only when set. Format 9 adds the compressor key (`param comp_key 1`), the chorus and key sends, the chorus `mix` settings and lanes on bus and master settings (`lane 0 reverb_decay ramp`). Format 10 adds song markers (`marker 2 verse`: an entry and a name), in song order, one per entry and each name once, checked against the song once the whole file is read. Markers stay out of the engine; edits that insert or remove song entries move them, and a removed entry takes its marker with it. Format 11 adds a `parts` line to a track block, one word per song entry (`.` follow, a pattern, `-` rest) up to the track's last part of its own, checked against the song once the file is read. Each parameter knows the format that introduced it, so an older file cannot name a newer one. Older files still load, with the newer fields at their neutral values. A chord must be written in canonical form (ascending, no duplicates, in MIDI range), so every file has exactly one spelling. Parameters are stored by a stable `id`, not by index, so instruments can gain parameters later without breaking old files. Floats use Rust's shortest round-trip formatting, so save → load is lossless. Loading validates every value; it reports errors with line numbers instead of silently clamping. Saves are atomic: the file is written to a temporary file and then renamed over the target.

## Autosave

Every edit goes through `App::touch`, which marks the project dirty and increments a revision counter. Each UI frame, if the project is dirty, the revision differs from the last one written and the last write is at least 5 s old, the project is written to its autosave file with the same atomic save as a normal save (temporary file, synced, renamed). A failed write is reported once and retried at the next interval. Saving deletes the autosave and points later ones next to the saved file, also deleting any stale autosave that file had from an earlier session. A normal quit deletes it too, so an autosave found at start-up always comes from a session that did not end normally. Each session first locks its project (`song.tvo.lock`, an `flock` or a handle sharing no writing, which the system releases when the process ends) or a free untitled slot in the state directory, so no two sessions write one autosave and a running session's autosave is never taken for a crashed one's; saving under a new name takes the new file's lock first and refuses a file another session holds.

`run` enters the terminal before choosing the project, so the recovery question can be asked before the engine exists; a recovered project starts dirty, so it is autosaved again and the quit confirmation still applies. The main loop runs inside `catch_unwind`: a terminal error or a panic writes the autosave immediately, then the terminal is restored and the error or panic continues as before. The audio thread never takes part: autosaving reads the UI's copy of the project.

## Undo

`Project::inverse` returns, for any valid edit, the edits that restore the state before it. The UI records each change as an (undo, redo) pair of edit lists, and replays them through the same path as normal edits, so the engine stays in sync. Deleting a track inverts to inserting it back at its index and restoring every parameter and step. Track names and sample paths are not edits, so each history entry stores them before and after, and the UI sends the engine any sample that changed.

## Keys and colours

Every rebindable key is an `Action` in `keymap.rs`, which belongs to one `Context` (global, track, grid navigation, step, piano roll, automation, song, parameters). The handlers ask the `Keymap` which action a key is in the contexts active in the current view and never match key codes themselves. Contexts that are active together are listed in `TOGETHER`; `Keymap::check` refuses a key given to two actions in one of those sets, so a settings file cannot make a key ambiguous. A few keys stay fixed: the answers to questions (`y`, `n`, `Esc`, the instrument number after adding a track) and editing in text prompts. Hints, the key list and status messages show the first key bound to an action, so they follow the user's keys.

Drawing names a `Role` (cursor, playhead, muted, meter levels…) rather than a colour, and the `Theme` maps roles to styles. The built-in themes use the 16 ANSI colours, so they follow the terminal's palette; a settings file may also give a palette index (`ESC[38;5;n m`) or a 24-bit colour (`ESC[38;2;r;g;b m`). `tinvo settings` writes every action and role with its current value, and reading that text back gives the same settings (tested). The settings page (`Mode::Settings`) changes the live `Keymap`, `Theme` and mouse through the same checks, and on closing merges what it changed since the settings were loaded into the file as it is now (`settings::merge`, so another session's saves survive) and hands the old text and the result to `settings::update_text`, which rewrites only the values that changed and appends the others to their sections, then parses its own output and refuses to return text that does not read back as the new settings.

## Mouse

On Linux and macOS the terminal is asked for button, drag and wheel reports in the SGR encoding (modes 1000, 1002 and 1006), which arrive on stdin with the keys; `tui::input` decodes them, and the older encoding too, so its bytes are never taken for keys. Windows consoles deliver `MOUSE_EVENT` input records once `ENABLE_MOUSE_INPUT` is set; they say which buttons are down, so the terminal layer keeps the previous state to tell presses from releases and drags, and subtracts the window's origin from buffer positions.

While drawing, each view records which `Target` (a step, a track's mute column, a parameter, a list entry…) it put on which span of a row. A mouse event is resolved against the last frame drawn, so a click acts on what the user saw, and the geometry lives in one place. Clicks and the wheel go through the same action functions as keys. A drag extends the undo step its press made while that step is still the latest, so painting a row of steps or stretching a note undoes in one go.

- Autosave: written only for new edits and at most once per interval, holding the whole project, found again, deleted by a save and moved by a save under a new name, unreadable files set aside, a failed write reported once, the project lock (held until let go, links and directories at its name refused with their target untouched, also under another spelling of the path, a lock file left by a crash, a lock held by another process naming it and freed when that process is killed, untitled slots taken in order with a crashed session's first, saving refused onto a held file and moving the lock), and a recovery screen that takes only clear answers. The whole flow (edit, kill, recover, save; edit, kill, discard) was run on Linux in a pseudo-terminal.
- Fuzzing (`tinvo fuzz`, see `src/fuzz.rs`): mutated project files, WAV files and edit scripts, each checked against invariants beyond not panicking. Every accepted project must save to text that loads back equal and saves again identically, be rebuilt exactly by `to_edits`, and render without a non-finite sample. The WAV header reader, decoder, block reader, float re-encoding and the sampler's loader must agree bit for bit. Every edit must be undone exactly by `Project::inverse`, and a rejected edit must change nothing. Inputs that show a feature not seen before join the corpus; a failure is reduced and saved. CI runs each target for 60 seconds, and `cargo test` runs each briefly.
- Real-time safety (`tests/realtime.rs`): a counting global allocator is armed around every call into the engine, and must count nothing while the demo song and a heavy one play, while thousands of random edits, cues, auditions, sample changes and live-track changes arrive between callbacks of random sizes (1 to 4096 frames), while live notes come through the mailbox, while input is captured into the ring, and while MIDI bytes are parsed and posted. On a failure it prints the backtrace of the first allocation. It covers what the backends call, not the backend callbacks themselves.
- Performance budgets (`src/bench.rs`): four scenarios (the demo; the demo with every strip stage on and the mid band swept; a synth with eight voices of four-voice unison, noise and LFO; a sampler with eight voices through sinc and the filter). `tinvo bench --check` plays each in callbacks of 128 frames and fails if the mean callback costs more than its share of the period: 15 % for the demo, 25 % for the strip and synth scenarios, 10 % for the sampler, where two CI runs on Windows, Linux and macOS measured at most 2.8, 5.7, 6.2 and 1.2 %. These limits are loose because CI runners are shared and timings vary; they catch a scenario that stops keeping up comfortably, not a small regression. That is what the instruction budgets are for: on x86-64 Linux, CI counts the instructions per second of audio of each scenario with Valgrind's cachegrind, which does not depend on the machine's load (only on the code, the compiler and, a little, the C library), and fails if one is more than 10 % over `bench/instructions.txt`. `tinvo probe` exercises the real device, and `tinvo loopback` a real output and input together.
