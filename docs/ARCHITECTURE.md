# TINVO Architecture

TINVO is a terminal digital audio workstation written in Rust with **no third-party crates**: only `std`, its own DSP, and direct FFI to the operating system's audio and console APIs.

Author: 𝓐.𝓒.𝓑

## Design principles

1. **The audio thread is sacred.** After the engine is built, `Engine::process` never allocates or frees memory, locks, blocks or does I/O. Every buffer, voice and track slot is sized when the engine is created.
2. **One source of truth, one way to change it.** Every change to the document is an `Edit` value, apart from what the history keeps beside the edits and restores whole (track names, sample paths and zones, markers, plugin states). The UI applies it to the `Project`, gets back the edit *as actually applied* (with values clamped), and sends that same value to the engine. The model and the engine can't drift apart, because they run the same operations, and a test proves the edits rebuild the project.
3. **Offline equals real time.** WAV export drives the exact `Engine` used for playback, so an export renders the song as playback does (plugins aside, which render as fresh instances in offline mode, and what is played live, which is not part of the song) (the tests check that rendering is deterministic and independent of buffer size). Exports stream to a temporary file a block at a time, so memory use does not grow with their length; the header sizes are patched at the end and the file is renamed into place.
4. **Correct before clever.** Floating-point state is flushed explicitly instead of switching the CPU to flush-to-zero mode, because changing the floating-point environment behind the compiler is unsound in Rust. Timing comes from a fixed origin rather than being accumulated, so it does not drift.

## Threads and data flow

```
 ┌──────────── UI thread ────────────┐          ┌──────── audio thread ────────┐
 │ keys → App → Project::apply(edit) │  edits,  │ Engine::process(buffer)      │
 │                 │ applied edit    │ play/stop│   drain commands             │
 │                 └──► EngineLink ──┼──SPSC───►│   fire due note-offs/steps   │
 │                                   │  queue   │   render instruments         │
 │  meters, playhead, CPU load ◄─────┼─atomics──│   mix (gain/pan smoothing)   │
 └───────────────────────────────────┘          └──────────────┬───────────────┘
                                                               ▼
                                               backend converts f32 stereo to the
                                               device format (F32/I16/I24/I32)
```

- **Recording**: the backend's capture thread converts the device format to `f32`, keeps the first one or two channels and pushes whole frames (`[f32; 2]`) into an SPSC ring of 2^20 frames; it never blocks, allocates or writes to disk. A full ring drops whole frames and counts them, so channels never swap. The UI thread drains the ring every frame into a `wav::FileWriter` (32-bit float, written to a temporary file and renamed when the take ends). Stopping joins the capture thread before the last drain, so every captured frame reaches the file. The take then loads like any other sample. The recording keeps the index of its sampler track up to date as tracks are inserted or removed, through the same path every edit takes.
- **Live notes**: the MIDI backend calls a handler on its own thread (WinMM's callback thread, a TINVO thread polling the ALSA sequencer or rawmidi, CoreMIDI's receive thread). The handler pushes each note into two `rt::Mailbox`es: one the audio engine drains at the start of every callback (up to 256 notes), one the UI drains every frame for step entry, at most a mailbox's worth a frame. The backend threads check for closing inside their read loops, so a source that never pauses cannot keep them running. A mailbox is an SPSC ring with a try-lock on each end, so a push or pop never waits: it fails at once if the other thread of the same side holds the lock. That makes it safe while a closed input's thread and a new one overlap, or an old engine and its replacement do. The mailboxes live for the whole session and pass from engine to engine when the audio device changes; notes queued while no engine listened are discarded. The mailboxes carry the decoded MIDI messages (notes, controllers, pitch bend, and `Lost` for everything let go). A channel plays every track `Edit::SetChannel` gives it, or else the track named by `Command::SetLiveTrack`, which travels in the command queue, so it stays ordered with the edits. Each held note remembers its track and channel, so its release reaches the right voice after the selection moves; a channel's sustain pedal marks released notes as sustained, and lifting it releases them. The engine keeps each channel's pitch bend and mod wheel and, whenever they or the routing change, sets every instrument's from the channels that play it (the live track also takes those of the channels no track has: bends add, the highest wheel counts); instruments read them once per chunk. Recorded keys are held by channel and note, decided when pressed, so a release or a lifted pedal ends the right one whatever is selected by then. Only notes go to the UI's mailbox, and a bend or wheel message that finds the engine's mailbox full is dropped without letting notes go. Track additions and removals release every live note before indices shift.
- **MIDI output**: a track switched to MIDI out (`Edit::SetMidiOut`) sends its hits instead of sounding them, through the same queued-hit path, so swing, ratchets, micro-timing and chance are the same. Each message goes into an SPSC queue of plain `OutEvent` values (8192 deep; a full queue drops the message) stamped with its engine frame plus the engine's latency (the look-ahead of the limiter and of the master's chain, and the delay latency compensation adds). The engine sends its own note-offs on their frames, alongside the voices' note-offs, and releases every note it sent on Stop, on retrigger, when the track is muted or soloed away and when MIDI out goes. With `Command::SetMidiClock` on, `render_block` sends a clock byte on the frame of every transport pulse (24 per quarter note) inside the block, so clocks follow tempo points and ramps and land on the same frames at any buffer size; a song entry that starts between two 16th notes sends its Song Position at once and Continue with the first clock on a 16th. The latency is read again on every pass over a frame, so a limiter automated on inside a callback moves the frames from the hit that switched it. At the start of every callback the engine pushes an anchor: its first frame, its length, the rate and the `Instant` it started. A backend that renders one device callback in parts (JACK, in parts of 1,024 frames) says so first (`AudioCallback::begin`), and the engine anchors the whole callback once instead of each part. The output thread (`midi::schedule`, its own thread) keeps messages in the order the engine queued them and sends each when it is due, one due early waiting for those before it: a frame is heard one buffer after its callback, the estimate of when frame 0 is heard keeps the earliest anchor and moves later by at most 1 ms per second, and `midi_delay` is added. A note-on or clock more than 50 ms late is dropped, and a release of a note never sent with it; releases and transport are not dropped for being late, and one the output refuses stays first in line for up to a second; then a release or Stop is owed, and tried again on every look until the output takes it, while a refused Start, Continue or Song Position is dropped. Keys are counted per channel, so each start has its release, and since nothing overtakes what was queued before it, a limiter switched off between a note's start and its release cannot send the release first, nor Start before an earlier Stop, nor a reset before what it lets go. Clocks pass only while the thread has seen Start or Continue and no Stop since. A message lost to a full queue sets a flag; the next callback that finds room pushes a `Reset` with its anchor, before it handles any command, which in frame order releases every note sounding and stops the receiver unless the clock runs, staying first in line while the output refuses part of it. The anchor goes first in every callback, and each command reads the latency again, so what a command queues is stamped with the limiter as it is. With no anchor for 250 ms beyond four of the longest callbacks seen, the thread takes the engine for gone and releases everything; what the output refuses then is owed too, and the engine's messages wait until nothing is owed, so an old release or Stop cannot follow a new engine's notes and Start. They wait a second at most: an output that refuses longer gets them while what is owed is still tried, which may then come after them (on closing, the thread waits 200 ms for it). The queue lives in an `OutSlot` (`Arc<Mutex<Option<Consumer>>>`) that each new engine fills and the thread takes with `try_lock`; taking a new one, or closing, releases every note still sounding and sends Stop to a running receiver. A queue taken keeps what follows the first message due (with the delay) from 50 ms ago on, also from callbacks before the thread started, so a Play made just before is not lost; what came after the last anchor the previous thread took cannot be placed in time and is dropped. Every note-on the engine sends carries a tag of its own, and its release the same one: a note-on dropped as late or refused skips its own release, not that of another note on its key.
- **Recording notes**: while recording, the engine reports each live note on the live track at its nearest step (with its offset in ticks, and whether that step has played yet) and each step that track plays, through a third SPSC queue of plain `Take` values. The engine also measures each note's length in the track's steps when its key is released (or recording stops), against the step positions it plays, so swing and ramps are counted exactly. The UI collects them into a `NoteTake` and writes it as step edits in one undo step. Overdub merges them into the steps; replace counts the passes over each step and keeps the notes of the last. The engine counts the record commands it has handled in `Shared`, so the UI writes the take only once that count matches what it sent: every report pushed before the stop is in the queue by then. Track insertions and removals made while recording reach the take in the order the engine applied them: the UI queues each, and the engine pushes a `Layout` marker after applying it, where the take moves the tracks of what came before. A count-in is the engine's own: it clicks each beat on its exact frame and starts the transport on the frame the last beat ends. A take holds at most 100,000 keys; once full it stays full, even when a track removed takes some away, leaves out (and counts) the keys pressed after and counts no more passes, so replacing keeps what it holds.
- **Command queue** (`rt::spsc`): bounded, wait-free, cache-padded. If it is ever full, `EngineLink` keeps the remaining commands in order and retries every UI frame, so no edit is lost. The audio callback spends a fixed work budget on commands per call (track additions and removals, which move whole track slots, count 512 simple edits), so a UI that keeps sending cannot stretch a callback; the rest wait, in order, for the next call.
- **Telemetry** (`engine::Shared`): playhead step, per-track and master peaks (lock-free `fetch_max` on the bit patterns of non-negative floats), and smoothed callback load.
- **Sample buffers**: the UI loads each WAV file once into an `Arc<Sample>`, builds a track's zones over them into an `Arc<SampleMap>` and sends it in a `SetSamples` command. When the engine lets go of a map (replaced, track removed), it pushes the `Arc` into a second SPSC queue back to the UI, which drops it there, so the audio thread never frees memory. The UI counts what it has handed to the engine and not yet received back (sample maps, plugin instances and inserts share the count, which starts at what the engine was created with), and holds a command that carries one in its backlog while that count would pass the queue's capacity. Everything the engine holds or releases was counted so and is released once, so the engine's push into the return queue cannot fail. The UI keeps loaded samples by path: those the tracks play, and those the undo and redo steps refer to while they fit in a budget of their own as large as the project's, the steps nearest the present first, undo and redo alike, so undo usually restores a sample without reading the disk. A step whose samples were let go reads them again when it is undone or redone.
- **Start-up**: the backend opens the device first, then calls a factory with the real sample rate: on its audio thread (WASAPI, ALSA), or, where the system owns the thread that renders (CoreAudio, JACK), on the thread that opens the stream. That is when the engine is allocated, before the stream starts.

## Engine

- **Tracks**: up to 32 slots, each with an `Instrument`, a 64-step pattern, fader/pan/mute/solo, and smoothed left/right gains (5 ms time constant, so changes never click).
- **Transport**: a clock of 24 pulses per quarter note. Each pattern's steps are a whole number of pulses (1/8 = 12, 1/8T = 8, 1/16 = 6, 1/16T = 4, 1/32 = 3), so every division falls exactly on the clock. The frame of a step at pulse *p* is `origin_frame + round((p/6 + swing(p) − origin) × samples_per_16th)`, where `swing(p)` delays the second step of each pair by `percent/50 − 1` of a step and is 0 for triplets; for 16ths this is the same arithmetic as before pulses, so older projects play bit for bit as they did. Each track keeps its own next step, on the division of the pattern it plays; the entry's own grid publishes the play position, and a track's own pattern is cut where the entry ends. A tempo change moves the origin to the current position (but never past a swung step still waiting), so the playhead stays continuous. Tempo points live on the song: each song entry starts at the tempo of the last point at or before it (the set tempo before any), held, or with ramping on, moving in a straight line in pulses to the next point. At each entry the transport takes a new origin at its exact fractional frame, with the entry's start tempo and slope; under a slope the frame of a position is the integral of the time per 16th, `15·sr/slope · ln(1 + slope·Δ/bpm)`, and its inverse finds the position of a frame, so a ramp is exact and the same at any buffer size. Exports of the song or a region sum the same integral per entry. With no tempo points the old arithmetic runs unchanged.
- **Steps and hits**: a step is a note or a chord of up to 4 notes (stored as intervals above the lowest note) with velocity, length, chance, ratchet and a micro-timing offset. When the transport reaches step *n* it queues hits, never plays them directly: step *n*'s on-time and late hits, and step *n+1*'s early ones. An early hit is at most half a straight step early, and the shortest swung step is half a straight step, so an early hit is never due before it is queued. Every queued hit fires through the same path, after note-offs and the choke check, at its exact frame.
- **Patterns and song**: each track slot holds the steps of all 16 patterns, each pattern has a length, and the song is a fixed array of pattern numbers. Each track also holds a part per song entry: follow the entry's pattern, play its own pattern (from the entry's first step, wrapping when shorter and cut off with the entry when longer), or rest; `part_position` maps the playing position to the pattern and step a track plays, and the hits, the automation segments and the UI's play column all go through it. Song entry edits move every track's parts with the entries. The engine keeps the position of the next step to play (song entry, pattern, step) and advances it one step at a time: to the next step, at the end of a pattern to the cued pattern or the next song entry, and at the end of the loop region back to its start. Because early hits of a step are queued while the previous step plays, the next position is fixed when the previous step starts; a cue or song edit made after that applies from the step after. A position made invalid by an edit (shorter pattern or song) is corrected before it is played. The playhead (entry, pattern, step) is published as one packed `u32`, so the UI never reads half of an update.
- **Automation**: each track has 4 lane slots. A lane's target (`LaneTarget`) is a parameter of its track's panel (volume, pan, then the instrument's parameters), a bus or master setting, a group setting, a parameter of an effect in a track's, group's or the master's chain, or a CLAP plugin's parameter by its stable id, and its points are stored per pattern and step (NaN means no point, so the audio thread needs no `Option`). When a step fires, hold lanes write their point's value before the step's hits are queued. For ramp lanes the engine keeps one segment (start frame and value, end frame and value) from the current point to the next point in the pattern; ramps interpolate in the parameter's unit space (`ParamSpec::to_unit`), so log-scaled parameters glide geometrically, and both ends carry the exact point values. Ramps are evaluated on a 32-frame tick aligned to the absolute engine clock, and the render loop splits blocks at tick boundaries, so the result does not depend on the buffer size. The knob value is kept as the base: it is used before the first point of a pattern and restored on stop, and `SetParam` on an automated parameter only changes the base.
- **Channel strip** (`strip`): each track's mono signal runs through high-pass, low shelf, mid bell, high shelf, compressor and drive before the fader and pan. Its parameters follow the instrument's in one index space (`strip::track_param`), so the panel, the project file and automation lanes treat them alike. A parameter change sets a target; every 32 frames the strip moves each value about 1/30 of the way there in the parameter's own scale (a 20 ms time constant) and snaps once it is within 10⁻⁴ of the range, recomputing filter coefficients only while something moves. The countdown to the next update is strip state, so splitting a buffer differently gives the same output. A stage runs only while it changes the signal (a band is switched out once it is flat and its filter state is zero, the compressor once it is neutral and fully released), so a neutral strip is a bit-exact bypass. The high-pass and the drive are not transparent even at their lowest settings, so they crossfade in and out over 10 ms instead of switching. An opened project snaps every strip to its settings, so a render and live playback agree from the first frame.
- **Buses and master** (`mix`): after the strip, each track's signal is faded and panned into the mix; its sends tap that stereo signal (post-fader) into a delay bus, a reverb bus and a chorus bus, with send levels as further track parameters after the strip's. A fourth send feeds the key bus from the instrument's output, before strip and fader; every instrument renders before any strip runs, so the key bus is complete when a compressor switched to it reads it. The bus returns are added to the mix, the master fader follows, and the true-peak limiter runs last, segment by segment like the tracks, so an automated bus or master setting changes on its own frame whatever the buffer size. A bus is processed only while something is sent to it or its tail is still above −180 dB; with no sends and the limiter off the signal path is exactly what it was without buses. The limiter adds its look-ahead (about 1.6 ms) to playback latency; offline renders run that far ahead and drop it, so exports start on the first beat. Bus and master settings are global: `Edit::SetMixParam`, saved as `mix` lines. A lane on any one track can automate one of them (a lane's target is a `LaneTarget`: `Track` for one of its own track's parameters, `Mix` for a bus or master setting); the automated value overrides the setting until the lane lets go, its track is removed or playback stops.
- **Meters**: once a block the engine takes each compressor's and the limiter's gain reduction and feeds the output to a live BS.1770 meter (fixed memory: a ring of 100 ms sub-blocks and a histogram of 400 ms block loudness); the UI reads them through `Shared` with the peaks.
- **Chance**: rolled per step when its hits are queued, from a seeded generator that restarts on Play, so playback and export always produce the same sequence of hits from the start. Ratchets split the (swung) step span evenly, starting at the shifted position.
- **Groups** (`group`): up to 8 group buses (`MAX_GROUPS`) in fixed slots, like tracks. A track's group takes its post-fader signal into the group's stereo sum instead of the master's; the track's own sends still go straight to the buses. Changing a track's group crossfades from one sum to the other over 10 ms; changing it back before the fade is over turns the fade round where it is (a third place takes the share still on its way out at once). A group runs a two-channel `ChannelStrip` (the same stages; one compressor detector on the louder side, so both sides duck together), its fader and balance (both sides at unity in the centre), and its post-fader sends, and adds into the master's sum after the tracks. There is no key send: the key bus is fed from the instruments. A group runs while a track feeds it (a removed track only while its own fade lasts) and for two seconds (`HOLD_TIME`, long enough for the strip's most resonant setting to fall some 240 dB) after the last frame one did, counted in frames so it stops on the same frame at any buffer size. Then its strip lets go of what it held (filter states, the compressor's reduction); idle, it costs nothing and its glides land at once, so a track routed in later hears its settings and nothing of the past. At its defaults it passes its sum through bit for bit. Muting a group silences its tracks through their own gains, ahead of solo, so MIDI-out tracks in it release their notes. A lane on any track can automate a group's volume, pan, strip and sends (`LaneTarget::Group`). Inserting or removing a group renumbers the tracks and lanes after it. A removed group moves to one of 8 slots past the project's (`2 * MAX_GROUPS` in all), where it plays on, with the tracks still crossfading out of it, until its hold is over (with all 8 busy, one only ringing out is cut short first; failing that the first, whose tracks drop the share still fading out of it); the project refuses to remove a group that a track or lane still uses, and the editor's delete frees it first, in the same undo step. Group names are kept with the editor's metadata, like track names. A stem holds a whole group, since a group's compressor and drive are not linear in any one track.
- **Insert chains** (`insert`): every track, group and the master has a `Chain` of 8 slots (`MAX_SLOTS`), with holes; a project holds 64 effects (`MAX_INSERTS`). An `Insert` is one effect kind (`EffectKind`): the EQ, compressor and drive are a `StereoStrip` with only those stages set, the delay, reverb and chorus the bus effects with a dry/wet `mix`; the filter, phaser, bit crusher and gate are inserts only. Parameter 0 of every kind is its bypass. A track's chain runs after its strip on the track's signal made stereo, before its fader and pan; a group's after its strip; the master's after its fader and before the limiter. Effects are built off the audio thread: the editor turns `Edit::SetSlot` into `Command::SetSlot` with a boxed `Insert` (applying the edit itself, the engine builds one, which only offline rendering does), and every effect the engine lets go goes back through the release queue (`Retired`, 512 places, enough for what the engine holds, the removed groups whose plugin tails keep them playing included, and what is on its way back). A structural change (an effect in, out, replaced, or two slots swapped) is a pending permutation plus new boxes: the slots it touches fade out over 480 frames at 48 kHz, the permutation applies on the frame they are out, and the new contents fade in; a change made before then joins the pending one. The fades are counted in frames, so a change lands on the same frame at any buffer size. Bypass crossfades the same way, and a bypassed delay-type effect runs silence through until it is idle, so it never brings back old echoes. A group stays live while its chain is not idle; an idle group settles chain changes and settings at once. A lane names the effect kind it automates (`LaneTarget::Slot`, `GroupSlot`, `MasterSlot`); the project refuses to change the kind of a slot a lane automates, and a swap moves the lanes with their effects. Stems are taken before the master's chain, like the limiter.
- **Latency compensation** (`align`): the gate looks ahead (1.5 ms), so it delays its signal by that many frames whether or not it is bypassed (`Insert::latency`); taken out of or put into a chain, it crossfades with its undelayed input, so the change of latency is a crossfade, not a jump. A chain's latency is that of the gates in it and what its plugins report, and a plugin instrument's adds to its track's (one being taken out no longer counts, so the paths around it catch up while it fades). At the start of every segment the engine makes the chain changes due and plans: a track in a group is delayed to its group's slowest track, and every group and every track that goes to the master to the slowest path (`compensation`). Each track and group has an `Align` after its chain, a delay line long enough for 16 gates and 500 ms of plugin latency that crossfades between its old and new taps over 10 ms; with no delay it writes nothing and leaves the signal untouched. Segments end where a chain change is due, and, while there is a delay, where a group with no track rests, so the delays change on the same frame at any buffer size. A delay switched on waits until it holds that much input before it crossfades, and a second change on the same frame replaces the first. `Engine::latency` is the compensation plus the master chain's and the limiter's look-ahead: MIDI out is stamped that much later, the count-in click goes through an `Align` of its own, and export and stems drop that many frames at the start, so a stem lines up with the mix. A group still ringing out with no track left, or removed and playing on, keeps the latency its tracks had, and the others stay lined up with it. Commands replan before they run, so a note or a Start they send goes out as late as the sound. Known limits: a grouped track's own sends are ahead of its group's output by the group's latency and its compensation; a sidechain key is not delayed, so a keyed compressor or gate after a delayed path hears its key early by that delay; a gate switched on waits for its look-ahead of input before its crossfade while the paths around it start theirs at once, so for those 10 ms they can be apart by its look-ahead; a track crossfading to another group, or fading out after removal, is delayed for where it goes, so for those 10 ms it can be off by a gate's look-ahead; an export whose limiter a lane switches on or off at the very start keeps the latency the limiter had before.
- **Removal**: a removed track's slot is swapped with an idle one of 16 fading slots (`MAX_FADING`; a removal while all are busy cuts the oldest fade short), which the engine renders like a track (instrument, strip, fader, sends; no new hits) under a linear 10 ms fade, then releases its sample. The swap moves the slot's contents without allocating, and with no fade running the render skips the slots.
- **Choke**: when a closed hat fires, open hats on all tracks fade out over 12 ms.
- **Sample-accurate events**: each 64-frame block is split at every step boundary and note-off inside it. Note-offs fire before note-ons that land on the same frame.
- **Voice identity**: `note_on` returns a `VoiceId`, and note-offs target that exact voice, so retriggering a pitch never cuts off the wrong note.
- **Pan law**: constant power, −3 dB at centre. The bottom of the fader range (−60 dB) means silence.

## DSP

| Block | Method |
|---|---|
| Oscillators | Saw and square with PolyBLEP, triangle with PolyBLAMP, sine; phase kept in f64 |
| Filter | TPT/ZDF state-variable filter (LP, unity-peak BP, HP); stable under per-sample modulation |
| Envelopes | Linear attack, exponential decay/release (times are to −60 dB); retriggers start from the current level |
| FM synth | Four sine operators per voice, phase-modulating one another along one of eight algorithms, run from operator 4 down so a modulator's sample is ready for what it modulates; operator 4 is fed back the average of its last two outputs, which keeps a high feedback from flipping every sample. Per 64-sample chunk, Carson's rule bounds every operator's spectrum: its frequency, plus its peak deviation (each sounding modulator's index times that modulator's own peak frequency), plus the widest modulator's spectrum, twice once the indices add up to 1. The share of its modulation an operator keeps is the largest (found by bisection) that holds the bound under 45 % of the sample rate; a heard operator above that fades out by Nyquist. Levels and those shares glide over 64 frames when they change, so a stolen voice does not click and the output does not depend on the callback size. No oversampling, so no latency |
| Synth modulation | One LFO per synth, computed per 64-sample chunk, free-running in Hz or synced (one cycle per note value at the current tempo, its phase reset when playback starts), to pitch, pulse width, cutoff and level; glide is exponential in pitch (99 % of the interval in the glide time); pitch is recomputed per sample only while gliding or under LFO pitch modulation |
| Unison | Up to 4 copies of each oscillator spread evenly across ±detune, started at random phases and summed at 1/√n so the level stays steady |
| Sampler | Zones by key and velocity, round robin counted per zone or drawn at random (a seeded generator, so a song plays the same each time), release zones, and a loop mode per zone (the track's, none, one-shot, continuous, or sustained while held) with its own loop points or the file's `smpl` loop; 16 voices. Samples are limited to ±1024 (+60 dBFS) when loaded, with non-finite values silenced, so the gains after them cannot overflow `f32`. 8-tap windowed-sinc (Blackman window, 256 phases with linear blending between them) or linear interpolation, over a buffer padded with zeros so reads need no bounds checks; pitch ratio 2^(semitones/12) × file rate / engine rate; loops wrap exactly; a 64-frame fade at the region end; ADSR and an optional low-pass filter per voice |

The editor's run loop owns the stream. It opens the configured device, falling back to the default while that device is missing. A stream that reports an error is dropped and retried with backoff (1 s up to 8 s). ## CLAP plugins

`clap::ffi` holds the CLAP 1.2 types, written by hand from the 1.2.10 headers, with every function pointer an `Option` so a null one is refused, not called. `clap::library::Dso` loads a plugin file, checks its `clap_entry` (on Linux, through `dladdr`, that the symbol comes from that file), calls `init` with the file's path (the bundle's on macOS) and pairs it with exactly one `deinit` when dropped. The library itself is never closed: a plugin can leave code behind that runs after its `deinit` (the thread-exit destructors Rust's standard library and C++ `thread_local` register on threads that called into it, threads of its own), and unloading it would crash the next thread to exit. CLAP lets a file be initialised again after its `deinit`, so loading it again later costs only that.

Plugin code never runs in the process that scans. `clap::scan` finds the files, then for each one new or changed since the cache was written starts `tinvo scan-clap FILE RESULT` with its standard streams closed. The child turns off Windows' crash dialogs and joins a job that ends every process in it when the child ends (on Unix the parent starts it as the leader of a new process group; on Linux and macOS it sees the child end through `waitid` with `WNOWAIT` and ends the group before reaping the child, so the group's id is still the child's), reads the descriptors, calls the file's `deinit` and only then writes the result file, in a folder of the scan's own (mode `0700` on Unix) in the user's temporary folder (`tinvo-clap-scan 1`, one escaped, tab-separated line per plugin or one error line, then `end` as the last line). The parent waits for it against a monotonic deadline, the lesser of the per-file limit and what is left of the scan's budget, kills and reaps it past that, and takes anything but a clean exit with a whole result as the plugin's failure, which is cached with its reason like a success. What is the scanner's fault and not the plugin's leaves the file uncached, so the next scan reads it: a child that cannot be started, cannot write its result or have it read, or is cut short by the budget, and a file that changed while it was read. Entries the search did not reach (an unreadable or too deep folder, an entry whose type could not be read, a root after a limit) are kept; the rest of the cache is pruned to what was found.

`clap::host` plays plugins in TINVO's own process. A `PluginHost` is not `Send`, and is made on the program's main thread, which CLAP asks for on Windows and macOS. Each thread gets a number of its own the first time it asks; an instance's host data keeps its host's, and `clap.thread-check` reports the main thread for that instance only on that thread, so a second host on another thread is not mistaken for it. Plugin files are kept in one process-wide list, so a file is initialised once however many instances (the editor's, an export's) use it; a second path to a loaded file is recognised by the library handle the system returns, which is the same for one image. An instance holds its file, and files nothing else holds are let go of, with the list's lock held so a file's `init` and `deinit` never overlap, when an instance is dropped, when making one fails, and when a host polls or is dropped. Each instance has host data of its own at a fixed address (the `clap_host_t` the plugin was given, its token, its host's thread and the flags its callbacks set), outliving `destroy`. An instance is `Send`: it moves to the thread playing CLAP's audio thread, which marks itself with a flag of its own around every audio-thread call (an `AudioRole`), so the main thread can play that role too when it renders a file, stops an instance left processing or resets one to restart it. `on_main_thread` is called by the poll through a pointer the host data keeps, which CLAP allows while the instance processes elsewhere; only the instance's own thread can destroy it. Buffers (a plane per channel of every port, in a `Vec` that is never resized, its size checked and its memory reserved fallibly), the event list (512 events) and the held-note table are sized when the instance is activated or created, so processing allocates nothing; a held note keeps one event's room for its release. The number and the flag are read and set without allocating on any thread, the first time too, the system's audio threads included: Linux and Windows give a program's own thread-locals their storage as each thread starts, and on macOS, which gives it from the heap at a thread's first use of one (the HAL's audio thread's first callback), they live in two pthread keys' slots, which are part of the thread. A failed process call leaves the events it did not take queued until a restart clears them with their notes, and a non-finite velocity plays no note. An instance dropped off its host's thread stops processing there and is moved whole into its host's inbox, which the next poll empties on the main thread, destroying it there; once its host is dropped the inbox is closed, and an instance dropped later off that thread is leaked with its file. An instance reads its parameters (`clap.params`, at most 4096, passing over any without a real range (a stepped one's holding a whole number) or with an id already seen) each time it is activated, and its latency (`clap.latency`) right after; the latency may change only then, so `clap.latency`'s note of a change needs nothing more. `set_param` queues a parameter change by stable id, in range and a stepped one's truncated to a whole number within it, ahead of the notes in the next call (256 of them in room of their own, a later change to a parameter waiting replacing it, so a note's room is never taken); a change waiting when the instance is skipped reaches it through `flush` on the audio thread, but one CLAP marks `REQUIRES_PROCESS`, which waits for a process call. A restart keeps the changes for parameters still there and still settable, kept to their ranges as read again, and drops those of a parameter the plugin cleared all of (`clap.params`' clear with `CLEAR_ALL`), whose id may name another from then on. Each queued change carries a serial; the host data records the serial up to which every change has reached the plugin or was dropped, so its owner knows when a state saved has them. Changes the host made change what the plugin would save, as CLAP says, but are not reported as a dirty state: their sender knows of them, and an automation lane's are already in the project. The plugin's own changes to its parameters (output events) are noted as values to read again, and as a dirty state unless the parameter is read-only; `clap.params`' rescan and clear and `clap.state`'s `mark_dirty` are noted the same way, and the poll reports them (`Request::Params`, `Request::Cleared`, `Request::StateDirty`). A rescan of the parameters' info reads again, for the handles, the names and flags CLAP lets change while a plugin is active. A state (`clap.state`, at most 16 MiB, through streams that take and give it in parts, and that fail the save once it is too large whatever the plugin says) is loaded after `init` and before the first activation (`create_with_state`), so the plugin starts with the layout and latency that state gives it; one it cannot load fails the creation, since the plugin may have taken part of it. The main-thread calls CLAP allows while a plugin processes (a parameter's value, its text and the value of a text, and saving the state) go through a `PluginHandle`: it holds the instance's host data, never the instance the audio thread has, is neither `Send` nor `Sync`, and calls the plugin only on its host's thread while the plugin's pointer is set, which is cleared there before `destroy`. A poll forgets the host data of a destroyed instance even while a handle keeps it, with whatever it had asked for.

`clap::host::gui` hosts a plugin's own window (`clap.gui`) through the instance's handle, on the main thread. `gui_open` takes a window API (`win32`, `x11`, `cocoa`) and opens the window floating where the plugin offers that (titled through `suggest_title`, sized by the plugin), otherwise embedded: the caller's closure makes a `ParentWindow` first (on Windows, so the window's monitor gives its scale), then the plugin's window is made, given that scale where the system sizes in pixels (not on macOS, where it sizes in points), asked its size and resize hints, and put in the parent sized to fit, which is then shown. Any step that fails after `create` destroys the window before the parent goes, and the closure may use the handle itself (drop the instance, open the window), which is checked again after it. A `ParentWindow` is called with the window's state held, never over a call into the plugin, and reports what it learns (a drag, a close) later, from the main loop, rather than calling back into the handle. The instance keeps what is open (`GuiData`) in its host data, so a handle, the host's poll and the instance's teardown reach the same window. A drag reaches the plugin through `gui_resized` (`adjust_size`, then `set_size`, the parent snapped to what it took, or both sent back to the size they had agreed when the parent cannot take it), and a report of the size already agreed on, however often the parent makes it, is not sent back. The plugin's `request_resize` is answered by the parent at once when it comes on the main thread with nothing else holding the window, and is queued otherwise (CLAP lets such a call say yes and be applied later); the poll serves it, and a size the parent refuses sends the plugin back to the last one with `set_size`. `request_show`, `request_hide` and `resize_hints_changed` are recorded in atomics (a plugin may ask from any thread, the audio thread too, and waits on no lock), the latest show or hide winning, for the poll; `closed` too, a close winning over showing and a window the plugin destroyed itself only acknowledged with `destroy`, with no `hide` first, and the poll reports `Request::GuiClosed`. A plugin can destroy its window inside any call the host makes (`create`, `show`, `set_size`), so `closed(true)` is also noted at once, and opening, the poll and a drag check it between calls and go straight to that `destroy`. A size the plugin got on the main thread cancels one it asked for from elsewhere before, and wins over a drag it took meanwhile. Closing hides a shown window, destroys it, then drops the parent. An instance made to play in real time is offered `clap.timer-support` (periods of at least 15 ms) and, on Unix, `clap.posix-fd-support`; registrations are taken on the main thread only, belong to the instance rather than its window, and are served by the main loop through `PluginHost::next_timer`, `fds` and `dispatch`, which drains the inbox first, advances each due timer by its period before calling it (one long late runs once and is due a period after now) and checks each registration again before its call, since an earlier one can take a later one away; a descriptor's readiness reaches only a registration `fds` gave (each has a serial), not one made since for a descriptor that took the closed one's number. `clap::window::Windows` opens a plugin's window with the system's window API and keeps each by its instance's token. On Windows the main thread is made per-monitor DPI aware once (Windows lets a window be put in another only when both were made aware alike, and scales sizes for a thread aware otherwise than the window), and each embedded window gets a top-level window of TINVO's class whose procedure records a close, a client size or a new monitor scale for `pump`, which runs after at most 256 messages are handed out: a close closes the plugin's window and then TINVO's, the last size of each window goes to `gui_resized`, a scale to `gui_rescaled` (`set_scale`, then the window takes the plugin's size), and windows whose plugin closed them or went are let go of. A drag the user makes runs in Windows' own loop, so its sizes are served from the procedure as they come; a size TINVO sets itself is no drag (it may set one with the window's state held, from inside the plugin's `request_resize`). The frame lets the user size it only the ways the plugin resizes, and TINVO any size, though a captioned window has a least width and a size Windows gives otherwise is refused with the window put back. A move to a monitor of another scale puts the window where Windows suggests, so it stays under the pointer, then sizes it for the plugin. What a window recorded goes with it, so a close queued for a window closed meanwhile never reaches the one opened after, and each set of windows is handed only what its own recorded. A plugin's quit message is not TINVO's to end on. On Linux the windows are X11's, through Xlib loaded at run time (`libX11.so.6`, so nothing X11 is needed to build TINVO or to run it without windows), on a connection of TINVO's own opened with the first window and kept, with an error handler that ignores errors on that connection (Xlib's default ends the process, which a window gone before a request about it reached the server is no reason for) and passes any other connection's to the handler set before. Each embedded window gets a top-level window of TINVO's that asks the window manager to close through `WM_DELETE_WINDOW` and reports its sizes (`ConfigureNotify`); sizes are asked of the server, which a window manager may answer with another, coming back as a size like a drag's (the size it kept, reported again after one was asked for, is a refusal, not another drag to fit), and the size hints hold the axes the plugin cannot resize at the size the window has. A plugin window that speaks XEmbed is told once it is embedded when the window is shown, and mapped if it asks to be; one still in the window when TINVO's goes (its destruction may wait unsent on the plugin's own connection) is moved out first, so nothing of the plugin's goes with it. The plugin is given the scale `Xft.dpi` says (1 without it). The connection's descriptor is among those the main loop waits on (`Plugins::fds`), and the pump reads what it sent, handing each set of windows what is its own, then serves again what Xlib read meanwhile (while waiting on the server for something else), which the descriptor no longer shows. On macOS the windows are `NSWindow`s, through the Objective-C runtime (`objc_msgSend` called with each method's exact signature, never as a variadic function), with AppKit loaded when the first window opens, so TINVO's terminal use never loads it. AppKit makes windows only on the process's main thread, which TINVO's main loop runs on (opening one elsewhere is refused), and gives a process without a bundle no windows until it says what kind of application it is: TINVO is an accessory one, with windows but no Dock icon or menu bar. Each window's delegate records a close the user asks for (accepted, which only hides a window not released when closed, so AppKit does not beep; its plugin's window is destroyed at the pump before TINVO's is let go of) and the sizes it takes, a size TINVO gives making those recorded before it past; inside AppKit's own loop for a live resize the sizes go to the plugin at once, and a size TINVO sets itself is no drag. Sizes are in points, as CLAP's Cocoa windows take them, and the plugin is given no scale; a size AppKit does not give (it keeps windows within the screen) is refused with the window put back, and the axes the plugin cannot resize are held by the content's least and greatest sizes. AppKit's events wake nothing the terminal waits on, so while a window is open the main loop waits no longer than a frame (`Plugins::wake_within`), and each pump hands out what is queued, the window readied for a plugin that floats its own too. Each time round the main loop, and each serving of the plugins during an export, has an autorelease pool of its own (`clap::window::Pool`, nothing elsewhere), so what plugins autorelease on the main thread is let go of. An instance's window is closed after it stops and before it is deactivated and destroyed, on its host's thread (an instance dropped elsewhere goes home first), and whatever the plugin left registered is forgotten once it is destroyed. The editor opens windows through `Plugins` (`plugin_window` on a plugin's page), one for each instance it plays; it closes one whose instance no longer plays for its place (removed, replaced, picked again or gone) after each edit and each tick (one it gave up on after two failures too), and every one when the device is lost, when a new engine comes and with the editor; before an engine's instances are destroyed (its stream ended, so they came home), a dirty state no poll has reported is read from their handles (`take_state_dirty`), since the poll destroys the instances that came home first, and their states are saved; a device that fails to reopen goes the same way as one lost. It needs nothing for the plugin's changes made there: the panel reads the plugin's values, and the plugin's output events and its dirty state mark the project unsaved.

In the engine, a plugin plays as a track's instrument (`InstrumentKind::Plugin`) or an insert (`EffectKind::Plugin`), naming its plugin by a `PluginRef`: a `Copy` number for an id, interned once for the process (at most 4096 ids, never freed), so kinds stay plain values. The track or insert holds a `PluginSlot`: empty, playing an instance, or lent out under the instance's token. The UI thread makes instances and sends them in `SetPlugin` (a track's) or inside the insert of a `SetSlot`; an instance that does not fit its slot (another plugin, role or sample rate), or a plugin insert made for another sample rate than the engine's, comes straight back, stopped. Everything the engine lets go of goes back through the retirement queue, stopped on the audio thread first (CLAP's `stop_processing` belongs to that thread): an instance replaced, an empty slot's, a removed track's when its fade ends or it is evicted, an insert with its instance in it (counted as two in the queue's budget, since they can come back apart). To restart one, the UI sends `Lend(token)`; the engine finds the instance by token, stops it, queues the releases of the notes it holds (a restart clears them; given back without one, it lets them go) and returns it as `Retired::Lent`, and its slot waits for `Return`, which puts it back only into the slot that lent it, under the same token and still fitting, and otherwise retires it. Taking an instance out of a track forgets the notes the track held on it (its pending note-offs and its live keys), since the next instance gives its notes ids of its own. A plugin track is stereo: its instrument renders into a stereo buffer of its own, its strip runs on both channels (`TrackStrip::Stereo`), its pan is a balance law, and its key send hears the middle (L+R)/2. A removed plugin track, its inserts too, plays no further than its fade. A plugin insert processes its chain's buffer in place, or during a fade a copy of the dry signal; bypassed and faded out it lets time pass through `skip`. While its last call returned `CLAP_PROCESS_TAIL` it counts as holding sound, as a delay does, so its group does not come to rest on it; a plugin instrument's tail likewise keeps a render's end from coming while it lasts (up to the render's longest tail). A MIDI-out plugin track sends its notes instead of playing them, as any MIDI-out track does, and what its plugin plays of its own (a tail, or a plugin running free) is still heard. The engine touches thread-local storage only through its instances' calls: on macOS a thread's first such call may allocate, once, as a plugin's own thread-locals would, which no host can avoid on a render thread the system owns. A render plays a project's plugins through instances of its own (`render::PluginSource`): `Project::plugin_places` lists every plugin track and insert, and before a frame is rendered each gets an instance made for offline rendering at the render's rate, through `SetPlugin` or `SetSlotPlugin` (which puts an instance into the plugin insert a slot holds, or will hold once a pending move lands). The render runs on the thread of the host that made them, which plays CLAP's audio thread too, and serves their requests between chunks: a restart is done in place (lent, restarted, returned), and a failure, or a plugin that cannot load, stops the render with the plugin's name and the reason. Plugins run in TINVO's own process, so one that crashes ends it, leaving at most a temporary file behind. `CatalogPlugins` makes them from the scan's catalog, through a host of its own; making one is `unsafe`, as making an instance is (the files are trusted, and it lives on CLAP's main thread). `tinvo render` scans, with the cache, only when the project names a plugin, and renders, pads and writes every file, the stems too, before any is put in place. A stem mutes every group but its own: a group with none of the stem's tracks still runs its inserts, and a plugin there could sound from silence. The editor's plugins live in `plugins::Plugins`, on its main thread: a scan of the installed plugins on a thread of its own, started with the editor, whose catalog the editor takes when it comes, and which is called off and waited for when the editor ends, so no scanner process outlives it; the host the engine's instances come from; and the problems the plugin list shows until the next try. A new engine (a device opened or reopened, at its own rate) gets an instance for every plugin place, and so does the engine playing when the catalog comes. An edit that makes a plugin place, whether the user, undo or redo made it, gets one through `SetPlugin` or `SetSlotPlugin` after the edit; one picked from the list is made before the edit, even with no engine to play it, so a plugin that cannot load leaves the project as it was and is named in the list; picked again for its slot, it is loaded afresh in place, the slot's settings kept. A place whose plugin is not in the catalog or cannot load keeps its plugin in the project and stays silent. Each tick, the editor polls its host even without an engine (so instances that came home are destroyed): a restart asked for is served by lending the instance out, restarting it and giving it back; a failure is restarted once, and an instance that fails again stays silent whatever it asks after. Requests are served once per instance a poll, a failure first, never while the instance is lent out, and only for the instances of the engine playing, which the editor forgets as they come back. While plugins play, the idle loop wakes every 25 ms, within the 30 ms CLAP asks for. Export from the editor makes instances of its own through a separate host on the same thread, so its requests are not the editor's; the editor's own host is polled between the export's chunks and served after it, so the instances playing live are not kept waiting. When the stream ends, the backend drops the engine on its own thread, so its instances go home through their host's inbox; the main thread must keep its host alive until the stream has stopped. On CoreAudio, a stop or dispose that fails leaves a callback able to run, so the engine is leaked there on purpose, its instances with it.

A plugin's parameters reach it in the engine by stable id. `SetPluginParam` names a plugin place (`PluginPlace`, a plugin track or a slot of a chain), the plugin expected there and the parameter, with a serial for the UI to watch `delivered` for; it does nothing to another plugin, and nothing while a lane holds that parameter. A lent instance's changes wait in its slot (32 of them, a later change to a parameter replacing the earlier) and reach it when it is back, those its queue has no room for yet a block later. A lane can name a plugin's parameter (`LaneTarget::Plugin`, by where it plays from the lane's track: its instrument, a slot of its chain, of a group's or of the master's), with points that are the parameter's own values, glided in a straight line in a ramp lane, since the engine does not know the plugin's curve, and kept to the parameter's range as they are sent. With no point in force a lane leaves the parameter at its base (`SetLaneBase`), if it has one, and also when it is let go of or its track is removed; a lane on a group's or the master's plugin is the only one in the project on that parameter. A value goes out only when it changes, and a value in force again to an instance that has not had it: one that came (a `SetPlugin`, a `SetSlotPlugin` or an insert placed with its instance), came back from a restart, or could not take it. A base goes out only as the lane lets go of the parameter or as it is set, so a value set while the lane held nothing stays through an instance's return. Plugin latency counts in the compensation: a plugin instrument's adds to its track's chain, a plugin insert's to its chain, each instance's at most half a second (`MAX_LATENCY_SECONDS`, past which activating it fails with how late it comes), and each aligner can make up for that half second on top of every slot's gate. A path later than its aligner makes up for is heard early, and `Shared::latency_over` says so; a render refuses it. A plugin insert's input, for its fades and for standing in for it, goes through a ring as long as its latency (`Instance::delay_dry`), so a bypass, its fade or a failed call moves nothing in time. A late insert brought back after being skipped plays its input until its output is from after it was skipped, so nothing from before its bypass is heard; an empty slot, or one whose instance is lent out, passes its input as it comes. Chains count their latency again when an instance comes, goes or comes back, and a render lines every path up before its first frame (`Engine::settle_latency`), rendering ahead as far as it is late while the transport still stops at the musical end; a plugin whose restart changes its latency during a render fails it, since the frames rendered could not be lined up with the rest.

The editor keeps a handle on each instance it gives the engine, by its place, followed through every edit, and saves their states into the project (`Project::set_plugin_state`) before a save, an autosave, an export, a new engine, a lost device, a plugin picked again in its slot and an edit or a history step that removes one. A state whose bytes did not change keeps its storage, which the history shares. A plugin that cannot save keeps the state it had and is named: a save says so and leaves the project unsaved, an export says it played as last saved. An instance starts from the state the project keeps for its place, and the engine gives it the base of each of its lanes that holds no point, since the state may be from a point that did. One that cannot load its state plays at its defaults and is named; that state is kept, not saved over, for a version of the plugin that can load it. A plugin's own report that its state changed marks the project unsaved, and a quit that came before the report asks after all. A plugin put in its slot again starts afresh, and that is an edit undo brings back. Renders start their instances from the project's states too, and fail on one that cannot load its state.

The panel shows a plugin's parameters through the same handles: a plugin track's after its volume and pan on the instrument page, an insert's on the plugin page (`Page::Plugin`, the slot it was opened on, `App::plugin_page`), at `PLUGIN_INDEX` plus the parameter's position in the plugin's list, those it hides left out. A `Knob` stands for a parameter the editor shows and changes, a built-in one's `ParamSpec` or a plugin's `ParamInfo` and handle, so the panel and the automation view treat both alike: a plugin's values are written by the plugin (`value_to_text`), nudged in hundredths of its range (whole values when stepped) and drawn in a straight line between points, as the engine plays them. A change from the panel goes to the engine as `SetPluginParam` with a serial of the editor's; the panel shows the value sent until the handle's `delivered` serial reaches it, and a new engine's instance is sent again what the old had yet to get (`App::carried`), which a save waits on too. An instance with no room for a change yet does not acknowledge it: its slot keeps it and gives it again. It is not part of the project, so the history step it makes (`Change::param`) holds the values before and after and sends one back on undo and redo; nudges in a row make one step, like the built-in parameters'. Where a lane holds the parameter, the panel sets and shows the lane's base instead (`SetLaneBase`); a lane made from the panel starts with the plugin's value as its base (not a whole value the lane's `f32` would round to another), and undoing the first base of a lane that had none sends back the value the plugin had. A save or autosave taken before the plugin had a value sent to it leaves the project unsaved, and it is marked unsaved again once the plugin has it: each instance keeps the serial of the last value sent to it (`Live::sent`), compared with `delivered` before its state is saved, so a value that arrives while the state is saved counts as missing from it, however long the panel shows it; an export's states count for nothing here. A change refused, by the plugin or by the engine because a lane holds the parameter, is acknowledged too (`Instance::acknowledge`), after what was queued before it, so nothing waits on it. `A` on a track insert's page gives the lane to that track, which it selects. A read-only parameter is not set, and only an automatable one gets a lane. The plugin page follows its plugin through moves, tracks put back before it and undo, whichever track is selected, and goes back to the inserts page when it goes; a plugin given up on, or gone with its device, shows nothing to set. When a plugin clears a parameter's automation (`clap.params`' clear), the lanes on it are removed as one undo step; one it clears of everything may be another parameter from then on, so the history's values for it go too, from every instance of the plugin, and the steps left with nothing to do with them; renames and other steps around them stay. Known limits: undoing a lane such a clear removed brings back its base and points, which then reach whatever parameter has the id; undoing a lane's first base while a point holds the parameter during playback sends nothing back; a value sent to a plugin that has yet to get it when its slot or track is removed is not brought back by undo (for a bypassed plugin, one that needs processing waits that long); and a lane's values are `f32`, so a stepped parameter's lane takes no base past 2^24 that it would round. The editor names the plugins on a path when `Shared::latency_over` turns on.

## Project file (`.tvo`)

Line-based UTF-8 text with a version header (`tinvo 20`). Format 2 added `swing` and per-step chance and ratchet; format 3 adds the micro-timing offset and the chord (`-` or intervals such as `3,7,10`); format 4 adds a `sample` line to sampler tracks, relative with `/` separators when the file is inside the project folder; format 5 adds patterns (a `pattern B` line inside a track starts that pattern's steps; `pattern_length B 32` for lengths other than 16), `song A A B` and `loop <start> <end>`. Files of formats 1–4 load into pattern A. Format 6 adds automation: `lane <k> <parameter id> hold|ramp` and `point <k> <step> <value>` lines inside a track, with points belonging to the pattern of the preceding `pattern` line. Format 7 adds the channel strip's parameters as ordinary `param` lines; only values away from the strip's neutral defaults are written. Format 8 adds the sends (`param send_delay -12`) and the bus and master settings (`mix reverb_decay 2.4`), again only when set. Format 9 adds the compressor key (`param comp_key 1`), the chorus and key sends, the chorus `mix` settings and lanes on bus and master settings (`lane 0 reverb_decay ramp`). Format 10 adds song markers (`marker 2 verse`: an entry and a name), in song order, one per entry and each name once, checked against the song once the whole file is read. Markers stay out of the engine; edits that insert or remove song entries move them, and a removed entry takes its marker with it. Format 11 adds a `parts` line to a track block, one word per song entry (`.` follow, a pattern, `-` rest) up to the track's last part of its own, checked against the song once the file is read. Format 12 adds `pattern_division B 1/16T` for patterns whose steps are not 16ths and `pattern_meter B 6/8` for patterns not in 4/4, adds the synth's `lfo_sync` parameter, `tempo_point <entry> <bpm>` (one per entry, checked against the song once the file is read) and `tempo_ramp true`, and allows up to 8 ratchets; older files load with 16th-note steps in 4/4 and one tempo. Edits that insert or remove song entries move their tempo points, and a removed entry takes its point with it. Format 13 adds `midi_channel <1-16>` to a track block, only when set, and the synth's `bend_range` and `wheel` and the sampler's `bend_range` parameters. Format 14 adds `midi_out true` to a track block, only when set. Format 15 adds `group` blocks before the tracks and `group 1` in a track, `insert <slot> <effect>` and `insert_param <slot> <id> <value>` lines in tracks and groups with `master_insert` lines before them, and lanes on group and insert settings (`group1.comp_ratio`, `insert2.mix`, `master.insert7.bypass`). Format 16 adds CLAP plugins by their id, as a track's instrument (`track plugin <id>`) and in insert slots (`insert 0 plugin <id>`); an id is kept as written whether or not the plugin is installed, and must be one a project line can hold (no control characters, nothing a trim would take off its ends, at most 1023 bytes). Format 17 adds a plugin's state, as it last saved it, in base64 (`state <base64>` in a plugin track, `insert_state <slot> <base64>` after a plugin insert, `master_insert_state` before groups and tracks; at most 16 MiB each), lanes on a plugin's parameters by where it plays from the track and the parameter's stable id in decimal (`plugin.7`, `insert2.plugin.7`, `group1.insert0.plugin.7`, `master.insert1.plugin.7`), whose points are any finite number, and a lane's base (`lane_base <k> <value>`). Format 18 adds `zone` lines to a sampler track, at most 1024: `zone <low>-<high> <root|-> <low>-<high> <position>/<cycle> attack|release <cents> <dB> <start> <end|-> <path>`, the path last and kept as the sample's. Format 19 adds a zone's random range and mode before the path (`0-1 track`, `0.5-1 sustain:100-200`, `0-1 continuous` for the file's loop). Format 20 adds the FM synth (`track fm`). The time signature stays out of the engine's timing: it only places beat and bar lines. Each parameter knows the format that introduced it, so an older file cannot name a newer one. Older files still load, with the newer fields at their neutral values. A chord must be written in canonical form (ascending, no duplicates, in MIDI range), so every file has exactly one spelling. Parameters are stored by a stable `id`, not by index, so instruments can gain parameters later without breaking old files. Floats use Rust's shortest round-trip formatting, so save → load is lossless. Loading validates every value; it reports errors with line numbers instead of silently clamping. Files are read up to 256 MiB (settings up to 1 MiB), and a line is split into words only as far as its longest valid form. Saves are atomic: the file is written to a temporary file and then renamed over the target. A project a load would refuse (over 256 MiB, or with a plugin state over 16 MiB) is not written, so the file there stays as it was.

## MIDI files (`.mid`, `.midi`)

Export walks the same song entries, parts and steps as the engine, in musical time rather than frames: a step at its swung position (`Transport::step_position`), its offset in ticks of its division, its ratchets spread over the step as cut by the entry's end, and its length to the swung start of the step it reaches. It leaves out what playback does not reach: a step swing moves past its entry's end, unless it is early, and any hit due at or after the export's end. It does include what playback reaches beyond: the early hits of the next pass's first step, which sound before the end. An early hit sounds no earlier than playback queues it (`Engine::queue_early`): as the track's step before fires, or before that where that step is shorter than the hit's reach and the lookahead, one entry ahead, sees it; so after a short entry the track rests in, it waits for that entry to start. Ticks are 960 per quarter note, so the import's grid of 24 ticks per 16th-note step is a whole number of file ticks and an exported file reads back exactly. Tempo changes go on the first track: one per entry, or one per 16th note through a ramp, each the constant tempo that lasts as long as that 16th does under the ramp (`span_frames`). A note is ended where the same key starts again on its channel, since a MIDI receiver cannot hold one key twice; when another track strikes it, the release goes a tick early, because a player merging tracks may take two events on one tick in either order. Passes are capped at 32 so no delta time exceeds the 28 bits a file can hold, and an export of more than a million events, or one that walks more than a million steps of a track (silent ones too), is refused before it takes much memory.

Import parses every track, pairs each release with the oldest press of its key, and ends keys still down with their track. Notes become steps per (MIDI track, channel), and per drum on channel 10, then the grid is cut into patterns of whole bars (the most that fit in 64 steps), and again at each bar line where the tempo changes so the change is an entry's tempo point (one inside a bar from the next bar line), and compared entry by entry, so a repeat reuses its pattern. The reader keeps at most 200,000 notes and reads at most 16 MiB; what is left out is counted for the report. The project is then read again from its own export until the two agree (a pass or two): the export ends a held note where its key is struck again, puts an early note at the very start on the start and keeps drums a step long, and that can split entries that shared a pattern. Exporting an import therefore gives the same project back.

## Autosave

Every edit goes through `App::touch`, which marks the project dirty and increments a revision counter. Each UI frame, if the project is dirty, the revision differs from the last one written and the last write is at least 5 s old, the project is written to its autosave file with the same atomic save as a normal save (temporary file, synced, renamed). A failed write is reported once and retried at the next interval. Saving deletes the autosave and points later ones next to the saved file, also deleting any stale autosave that file had from an earlier session. A normal quit deletes it too, so an autosave found at start-up always comes from a session that did not end normally. Each session first locks its project (`song.tvo.lock`, an `flock` or a handle sharing no writing, which the system releases when the process ends) or a free untitled slot in the state directory, so no two sessions write one autosave and a running session's autosave is never taken for a crashed one's; saving under a new name takes the new file's lock first and refuses a file another session holds.

`run` enters the terminal before choosing the project, so the recovery question can be asked before the engine exists; a recovered project starts dirty, so it is autosaved again and the quit confirmation still applies. The main loop runs inside `catch_unwind`: a terminal error or a panic writes the autosave immediately, then the terminal is restored and the error or panic continues as before. The audio thread never takes part: autosaving reads the UI's copy of the project.

## Undo

`Project::inverse` returns, for any valid edit, the edits that restore the state before it. The UI records each change as an (undo, redo) pair of edit lists, and replays them through the same path as normal edits, so the engine stays in sync. Deleting a track inverts to inserting it back at its index and restoring every parameter and step. Track names, sample paths, sampler zones, group names, song markers and plugin states are not edits, so each history entry stores them before and after, and the UI sends the engine any sample that changed. An edit that may remove a plugin first saves every playing plugin's state into the project, and so does an undo or redo that may; a plugin place an undo or redo brings back gets its instance only once the state it had is back, and the instance starts from it.

## Keys and colours

Every rebindable key is an `Action` in `keymap.rs`, which belongs to one `Context` (global, track, grid navigation, step, piano roll, automation, song, parameters). The handlers ask the `Keymap` which action a key is in the contexts active in the current view and never match key codes themselves. Contexts that are active together are listed in `TOGETHER`; `Keymap::check` refuses a key given to two actions in one of those sets, so a settings file cannot make a key ambiguous. Actions added after settings files could already give their default keys away are listed in `keymap::LATE`: a key the file gives another action active with one of them is taken from its defaults instead of refused, so a file written for an earlier TINVO still loads. A few keys stay fixed: the answers to questions (`y`, `n`, `Esc`, the instrument number after adding a track) and editing in text prompts. Hints, the key list and status messages show the first key bound to an action, so they follow the user's keys.

Drawing names a `Role` (cursor, playhead, muted, meter levels…) rather than a colour, and the `Theme` maps roles to styles. The built-in themes use the 16 ANSI colours, so they follow the terminal's palette; a settings file may also give a palette index (`ESC[38;5;n m`) or a 24-bit colour (`ESC[38;2;r;g;b m`). `tinvo settings` writes every action and role with its current value, and reading that text back gives the same settings (tested). The settings page (`Mode::Settings`) changes the live `Keymap`, `Theme` and mouse through the same checks, and on closing merges what it changed since the settings were loaded into the file as it is now (`settings::merge`, so another session's saves survive) and hands the old text and the result to `settings::update_text`, which rewrites only the values that changed and appends the others to their sections, then parses its own output and refuses to return text that does not read back as the new settings.

## Terminal input

`tui::input` turns bytes into keys, mouse reports and paste markers, and `tui::term::Decoder` holds the bytes of a sequence that has not finished arriving. The rest of a sequence has 25 ms from when it was first waited for, however its bytes trickle in; then a lone ESC is the Escape key and anything else is dropped whole, so a sequence cut short never runs its last bytes as keys (bytes of it that come later still are read afresh). ESC followed by a printable byte is Alt with a key, which TINVO does not bind, and is dropped too. On Linux and macOS the terminal is asked for bracketed paste (mode 2004). Inside a paste the decoder looks for the end marker first, so a sequence cut short in the pasted text cannot take in the marker's bytes; the text becomes one `Event::Paste` of at most 8192 bytes (saying whether it was cut), never keys, and the editor puts it into an open prompt without its control characters, cut at the prompt's 4096 bytes with the prompt saying it is full. The Windows console sends a paste as keys. There, a key record's repeat count gives that many keys (at most 64), and UTF-16 surrogate pairs are joined into one character, a first half counting for the very next key press only. On Unix, SIGTERM and SIGHUP set a flag the main loop and the recovery question read: the session ends as on a terminal error, and the message says whether the unsaved edits were autosaved.

The main loop stops reading input once a frame (16 ms, counted from the first event) has passed and draws, so a busy stream never holds up the audio recovery, MIDI and drawing. Once neither input nor the drawn screen has changed for two seconds, it draws every 50 ms instead.

Its waits for input also wake for what plugins run on the main thread (`term::Wake`): on Windows any window message for the thread (`MsgWaitForMultipleObjectsEx`, with messages already queued counting), since a plugin's code relies on its windows' messages being handed out even when TINVO opened none; on Linux and macOS the descriptors the plugins wait on (and on Linux the X connection of TINVO's windows), polled with the terminal, each once (macOS reports only one of two entries for the same descriptor), their readiness kept in CLAP's flags until served (a wait for the rest of an escape sequence that one ends keeps its deadline). Each wait ends by the next plugin timer at the latest. After the input of a frame, the loop checks the descriptors once more without waiting, so input that keeps coming does not keep them waiting, then dispatches the plugins' timers and descriptors and pumps the window messages (`Plugins::serve_main_thread`). An export does the timers, descriptors (checked without waiting) and messages once a frame between its chunks; each asking for the descriptors is a round, and readiness found in an earlier round is not served, since a plugin may have registered another descriptor under the number meanwhile. Every wait of one poll, the rest of an escape sequence's too, ends by its timeout.

## Mouse

On Linux and macOS the terminal is asked for button, drag and wheel reports in the SGR encoding (modes 1000, 1002 and 1006), which arrive on stdin with the keys; `tui::input` decodes them, and the older encoding too, so its bytes are never taken for keys. Windows consoles deliver `MOUSE_EVENT` input records once `ENABLE_MOUSE_INPUT` is set; they say which buttons are down, so the terminal layer keeps the previous state to tell presses from releases and drags, and subtracts the window's origin from buffer positions.

While drawing, each view records which `Target` (a step, a track's mute column, a parameter, a list entry…) it put on which span of a row. A mouse event is resolved against the frame as it stands, drawn again without being sent, so the geometry lives in one place. A press, drag or wheel turn that comes after a key, a paste or a resize in the same batch of input is dropped, since the screen it was aimed at is no longer the one drawn; so is one already waiting when such a batch ran out of time, which the user aimed before seeing what the batch did. Clicks and the wheel go through the same action functions as keys. A drag extends the undo step its press made while that step is still the latest, so painting a row of steps or stretching a note undoes in one go.
